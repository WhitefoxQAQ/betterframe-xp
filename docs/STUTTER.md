# 「ガクッ」の種類と、このツールとの関係

このツールの文書には「ガクッ」「ガクつき」「カクつき」「ぐわんぐわん」という言葉が出てくる。**同じ言葉でも、原因の違う別の現象を指している。** どれを指しているかで、このツールで直せるか、そもそも関係があるかが変わる。この文書は、その区別をまとめたもの。

## この文書の読み方

- 根拠の強さを 3 段階で付けた。
  - **【測った】**: ログや計測値で確かめた。
  - **【見た】**: 作者が見た・感じた。1 人、Frame 1 台の体感。計測の裏付けは無いか、薄い。
  - **【推測】**: 仕組みから考えただけ。確かめていない。
- 「作者の環境では」と書いてあるものは、他の人で同じとは限らない。
- 作者の体感の時刻と、計測した「遅れたフレーム」の位置は、一度だけ突き合わせてある。メモした 10 件が全部、遅れたフレームが出た秒と一致した（作者の作業記録。このリポジトリには含めていない）。**1 回分の突き合わせで、種類 A についてだけ言える。**

## 一覧

| 種類 | 見え方 | 主な原因 | このツールが関係するか | 根拠 |
|---|---|---|---|---|
| **A. 1 フレーム飛び** | 一瞬だけ「コクッ」と引っかかる。単発か、数十回の群れ | Frame のコンポジタが、表示の時刻に間に合わなかった | **ある**（シャープの GPU 時間が乗る）。ただし、ない場合も多い | 【測った】 |
| **B. 首振りで引っかかる・行き過ぎて戻る** | 首を振ったときだけ、映像がぶれる | PC 側の予測とスロットルの切り替えと、Frame 側の再投影が噛み合わない | 直接は**ない**。作者の体感では、**パネルの「SteamVR」タブの視線の補正をオフにすると治る**（このツールが切り替えを用意している） | 【見た】（スロットルの切り替えは【測った】、仕組みは【推測】） |
| **C. 視界の端を見ながら動かすとき** | 視線を端に向けて頭を動かしたときの揺れ | Frame の視線を使う補正（再投影・目の位置） | レイヤーの処理とは**別**。作者の体感では、**パネルの「SteamVR」タブの視線の補正をオフにすると治る** | 【見た】（視線データの途切れは【測った】） |
| **D. スリープ後の「ぐわんぐわん」** | フレームレートは出ているのに、映像が揺れる。Frame を再起動すると、しばらくして安定する | Frame のコンポジタの内部の待ち（`Timed out waiting for signal thread`）が増える。原因は未確定 | **ない** | 【測った】（原因は【推測】） |
| **E. 映像そのものの乱れ** | カクつき、ブロックノイズ、映像が一瞬止まる | 無線の再送・パケット欠落、ストリームのリセット、エンコーダーの詰まり | **ない**（届く前の問題。シャープでは直らず、強調してしまうこともある） | 【測った】（一部） |
| **F. 72 Hz / 80 Hz での一定間隔の引っかかり** | 画面を 72 Hz か 80 Hz にしていると、一定の間隔で引っかかる | 未確定。Frame のコンポジタの「表示の完了を待つ」処理の失敗が、72 / 80 Hz のときだけ続けて出る | **ある**（シャープを掛けているときに出て、シャープを切ると止まった） | 【測った】（原因は【推測】） |

> 「PC の VRChat の fps が低い」は、ここに含めていない。fps が低くても Frame が届いた映像を再投影して出すので、首振りはガクガクしにくい（作者の記録）。fps の低さと、ここに挙げた現象は別。

## A. 1 フレーム飛び（遅れたフレーム）

**これが、このツールの文書で「ガクッ」と書いた場合の大半**。

- 144 Hz では 1 フレームが約 6.9 ms。その間隔が 13〜14 ms になる（1 フレーム飛ぶ）。計測では間隔 9.5 ms 超を「遅れ」として数えている。【測った】
- 作者が「ガクッ」とメモした 10 件は、すべて遅れが出た秒と一致した。つまり**小さな揺れではなく、1 フレーム分の遅れ**に対応している。【測った】
- 遅れは単発より**群れ**で出ることが多い（例: 数秒間に約 20 回）。【測った】
- レイヤーの計測の偏りではなく、コンポジタが実際に落としたフレームである（レイヤーの遅れ数と、コンポジタの dropped の増分が同じ秒に出た）。【測った】

### A-1. このツールの GPU 時間が原因のもの

頭を振り続けて、20 秒ずつ比べた結果（作者の作業記録の「4 通り比較」。このリポジトリには含めていない）。【測った】

| 状態 | 遅れたフレーム（20 秒、2 回） | レイヤーの GPU 時間 |
|---|---|---|
| 効果を切る | 14 / 14 | 0.53 ms |
| コピーのみ（シャープ 0） | 10 / 21 | 0.54 ms |
| 軽い版（`casCross` `casLuma` `cornerSkip` ON、シャープ 1.2） | 130 / 116 | 0.98 ms |
| 元の CAS（3 つ OFF、シャープ 1.2） | 336 / 333 | 1.42 ms |

- シャープの計算を入れると遅れが増え、GPU 時間の増え方と対応していた。
- 軽量化の 3 つで遅れは約 1/2.5 に減ったが、**0 にはならない**。
- 作者の体感でも、軽い版で「だいぶ安定した」。【見た】
- **この比較は 1 回きり、作者の Frame 1 台、頭を振り続けた条件だけ。** 普段の遊び方で同じ差が出るかは確かめていない。

### A-2. このツールが原因ではないもの

- **ホーム / ダッシュボードで頭を振ったときの小さなガクッ**: このツールを `streamOnly` で止めても、少し残る。【見た】
  - 残りの遅れは、コンポジタが「シェーダーのパイプラインを作る」「パススルーのカメラをつなぐ・切る」「vrlink が更新レートを通知する」のあたりに集中していた。映像なしの遅れ 54 件はすべて、これらのログ行の 10 秒以内にあった。【測った】
  - 作者は「通常プレイの範囲内」と判断した。（調査の記録はこのリポジトリには含めていない）
- **SteamVR 起動直後の遅れ**: 起動後の最初の 2 分に、遅れの 92% が集中していた（295 件中）。【測った】
- **ダッシュボードの開閉**: 120 秒の計測では、開いている間に遅れは増えなかった。ただし 1 回の計測。【測った】

### A-3. 分かっていないこと（矛盾を含む）

- **シャープ量と遅れの関係**: 作者の体感では「強めの設定ほどガクッとなりやすい」。【見た】 ところがコードを読むと、シャープ量は最後の掛け算にしか使われず、読む画素も計算の量も同じ。**この 2 つは今の情報では両立しない。** 量を変えて GPU 時間を測ろうとしたが、計測が止まっていて取れなかった。【測れなかった】
  - 量で重さが変わる経路として、画像の圧縮（UBWC）が効くかどうかが変わる説を考えたが、確かめられていない。【推測】
  - したがって、**「強さを上げても負荷は増えない」は、式から言える予想であって、確かめた事実ではない。** 体感と食い違うので、強さを上げて引っかかりが増えたら、下げて確かめてほしい。
- 軽量化の 3 つ（`casCross` `casLuma` `cornerSkip`）の、個別の寄与。
- 遅れが 0 にならない残りが、全画面の読み書きそのもの（効果を切ってもコピーが残る分）なのかどうか。

## B. 首振りで引っかかる・行き過ぎて戻る

- PC の SteamVR の「自動スロットル」が、負荷に合わせてフレームレートと予測の長さをその場で変え続ける。人の多い VRChat では、この切り替えが細かく何度も起きる。【測った】（切り替えのログがある）
- Steam Frame では補正が 2 か所にある。PC 側（予測・スロットル）と Frame 側（再投影）。表示の約 99% は Frame の中で再投影されたもの。【測った】
- 2 か所が噛み合わず、首を振ったときだけ目立つ、という説明は【推測】。止まっているときは姿勢が変わらないので気づかない。
- **作者の体感では、視線の補正（奥行き・目の位置）をオフにすると治る。**【見た】 パネルの「SteamVR」タブのスイッチで切り替えられる。→ C と同じ対処。
- 詳しい説明と対処の設定は、作者の作業場の調査記録にある（この配布物には含めていない）。

## C. 視界の端を見ながら動かすときの揺れ

- Frame には視線を使う補正が 2 つある（`gazeDepReprojectEnable` `gazeDepEyeToHeadEnable`）。作者の Frame の設定ファイルでは、揺れていた時期にどちらも `true` だった（Valve の初期値は、目の位置が `false`、奥行きは初期値なし＝無効）。【測った】
- **作者の体感では、この 2 つをオフにすると治る。**【見た】 後の検証で、スロットルなど他の設定よりも、この視線の補正をオフにするほうが効いていたと確かめた（作者）。
- 視線のデータはときどき途切れる（0.4 秒以上来ない `Large dt` が 696 回、最長 5.8 秒）。【測った】 途切れと揺れの関係は【推測】。
- パネルの「SteamVR」タブのスイッチで切り替える。これはシャープなどのレイヤーの処理とは独立で、SteamVR 自体の設定を書き換える（戻し方は SETTINGS.md）。他の人で同じとは限らない。→ [SETTINGS.md](SETTINGS.md) の「視線の補正」

## D. スリープ後の「ぐわんぐわん」

- Frame をスリープから復帰させるたびに、コンポジタが `Timed out waiting for signal thread after 1.01ms!` を出す回数が増えた（0 回 → 1 分に 50〜130 回）。Frame 本体を再起動すると 0 回に戻り、揺れも消えた。【測った】（再起動した直後から 0 回だった）
- PC の fps は 113〜141 出ていて、PC の重さではなかった。【測った】
- ただし、警告の数と揺れの大きさは比例しない例がある（1 分に 5〜53 回でも「めっちゃ安定」）。【測った】
- 原因は未確定。作者が Valve への報告文を下書きしてある。
- 詳しい記録は、作者の作業場の調査記録にある（この配布物には含めていない）。
- **対処: スリープを何度かはさんだあとに揺れたら、Frame を再起動する。作者の体感では、再起動のあと少ししたら安定する。**【見た】 ログでは再起動の直後から警告が 0 回なので、「少ししたら」の間に何が起きているかは分かっていない（起動直後の遅れが多いことは A-2 に書いた）。

## E. 映像そのものの乱れ

- 無線の再送やパケット欠落が増えると、映像が乱れる、一瞬止まる。`too many packets were missing even to retransmit. Aborting stream.` などがログに出る。【測った】
- 重い場面では、PC 側の `encode` が 5 ms から 17〜24 ms に伸びる。【測った】 全体の遅れ（`total`）は 48.6 ms から 62〜83 ms になる。
- コミュニティの報告でも、遅延・カクつき・パケットロスは最も多い不満の一つ（作者の作業場の調査記録による。この配布物には含めていない）。
- このツールのシャープは、**デコードの後**に掛かる。届く前の乱れは直せない。圧縮のノイズは**強調してしまう**。

## F. 72 Hz / 80 Hz での一定間隔の引っかかり

- 画面のリフレッシュレートを **72 Hz か 80 Hz** にしていると、映像が一定の間隔で引っかかる。作者の環境では、SteamVR を再起動したあとも、切り替えた 72 / 80 Hz で出続けた。【測った】
- 同じ時期のログには、Frame のコンポジタの `failed to wait for present` が出ていた。72 Hz では毎秒 17〜18 件の秒が続き、出ない秒もあった。80 Hz でも出た（件数は少ない）。144 Hz では、起動直後の 3 件を除くと、長い記録（5 時間ほど）でほぼ出なかった。【測った】
- 失敗の間隔は、72 Hz の**ちょうど 4 フレーム分**（平均 55.56 ms、ばらつき 0.4 ms）。ランダムではなく、周期的に起きていた。【測った】
- **シャープを切って素通しにすると、失敗は十数秒で止まった。** シャープを戻すと、2 秒以内に毎秒 18 件へ戻った。【測った】 試したのは作者 1 人、Frame 1 台の 1 回だけ。
- 原因は未確定。【推測】 Frame の画面の駆動と、コンポジタの待ち方が、72 / 80 Hz の周期でずれているのかもしれない。読みから、待ちの上限は約 15 ms と見られる（未確認）。1 フレームは 72 Hz で約 13.9 ms なので、その近さが関係するかもしれない。
- **なぜ 144 Hz では出ないのか、なぜ 72 Hz でだけ 4 フレームごとなのかは、分かっていない。**
- 120 Hz は作者の報告では問題なし。90 / 96 / 108 Hz は長く使っていないので確かめていない。
- **対処（今のところ）**: 144 Hz で使う。72 / 80 Hz で使うなら、シャープを 0 にする（`betterframectl set sharpenAmount 0`）。確かめたのは、シャープを切って素通しにした 1 回だけ。
- 作者 1 人・Frame 1 台の記録。他の人の環境で同じとは限らない。SteamVR の再起動（1 回の記録）では直らなかったので、再起動は対処にならない。

## 自分のガクッがどれか、見分ける

| 見え方 | まず疑うもの |
|---|---|
| 首を振る・ホームで頭を振ると、一瞬だけ引っかかる | A（1 フレーム飛び） |
| 重いワールドで、首を振るたびにぶれる | B（視線の補正をオフにして変わるか） |
| 視線を端に向けて頭を動かしたときだけ | C（視線の補正をオフにして変わるか） |
| スリープから何度か復帰したあと、全体がゆらゆら揺れる | D（再起動して、しばらく待って安定するか） |
| 映像が一瞬止まる、ブロック状のノイズが出る | E（無線） |
| 画面を 72 Hz / 80 Hz にしていて、一定の間隔で引っかかる | F（シャープを 0 にして変わるか） |

### A かどうかを数字で見る

- `betterframectl stats` の `gpuMsAvg`（このツールの GPU 時間）。`streamOnly = 1` で映像が出ているとき、運用値で約 1.4 ms（軽い版で約 1 ms）。
- **このツールを `off` にして、同じ動きで引っかかりが減るか**を見るのが一番確実。`betterframectl off` ですぐ素通しになる。減らなければ、このツールが原因ではない。
- D は、Frame の `~/.local/share/Steam/logs/vrcompositor.txt` の `Timed out waiting for signal thread` の数で見る。

## このツールの設定を上げすぎると

- シャープの計算は GPU を使う。A-1 のとおり、重い設定ほど遅れたフレームが増えた。【測った】 設定を上げて引っかかりが増えたら、下げるか `casCross` `casLuma` `cornerSkip` を ON にする。
- GPU の負荷が上がれば Frame は熱を持ち、ファンが回る可能性がある。作者の報告として、この注意はパネルと README に出している。**ただし温度とファンは、このツールでは測っていない。**【推測】
